# Feature 10 — System Monitoring and Documentation (Batch 10)
**Depends on:** all earlier batches (the monitored `run_local.py` calls Batch 02/06/07/09 modules; the monitoring page reads their tables).

**What it does.** Records every pipeline run (steps, durations, row counts, ERROR/INFO logs, ingestion statistics), summarises errors, shows pipeline health indicators (OK / WARN / FAIL) and the configuration status of external integrations. Adds the module, configuration and Python-API reference, the architecture update and the demonstration guide.
**How it works** (`common/monitoring.py`)
- `PipelineMonitor` is a context manager: `with run.step("name") as s: s.metrics(rows_in=…, rows_out=…)`. Records are buffered in memory and written **once** at the end (tables `ops.pipeline_runs`, `pipeline_steps`, `pipeline_logs`, `ingestion_stats`), so no database connection is open while dbt runs against the same file. A failed step marks the run FAILED and the exception still propagates; a monitoring write error only logs a warning.
- `system_health()` indicators: last run status, run age, dbt build result (last run), errors in 24 h, ingestion rejection rate, data-quality score, open critical alerts. Thresholds: `config/features/monitoring.yaml`.
- `integration_status()` reports only whether Kafka/Snowflake libraries and credentials are *configured*; it never opens a connection.
**Modified existing files:** `run_local.py` (monitored steps; `--skip-phase2`, `--report`, `--no-monitor` flags; the dbt-failure stop from the previous fix is unchanged and recorded as FAILED), `common/store.py` (honours `ATMOSYNC_DUCKDB`, the same variable dbt uses), `tests/conftest.py` (tests use a temporary ops database), `.gitignore`, `README.md`.
